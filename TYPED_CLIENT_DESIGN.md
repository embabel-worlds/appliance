# Typed clients and realm methods — working notes

**Status: a working note, not a decision record.** Captured mid-discussion so the
findings aren't re-derived later. Nothing here is committed to except where it
says "decided". Sibling to `SHARED_CLIENT_DESIGN.md`, which covers sharing the
two *front ends*; this one covers what a *third-party caller* codes against.

The question started as "do we need a TypeScript client library for the REST
interface, with generated types, so we can write OO code against queries?" It
ended somewhere more specific: **the client library already exists, and the thing
it cannot express is calling a realm's behaviour as a method on a graph entity.**

## What already exists, so nobody re-derives it

`@embabel/appliance-kit` is the client library. `ApplianceClient` with `.kg`,
`.handlers`, `.documents`, `.hints` and `.tours`; types generated by
`openapi-typescript` from `spec/client-surface.json`, which
`OpenApiClientContractTest` regenerates in the assistant and fails the build when
the published surface moves. The predecessor repo `embabel-appliance-client` is
marked superseded — there is one library, not two, and a new one is not the answer
to anything below.

Its failure model is worth knowing before designing on top of it. Every method
returns `Outcome<T>` rather than throwing, because the failure that matters most
is not an error: `'unsupported'` means *this appliance predates the endpoint*, and
an app installed in March talking to an appliance pulled in August needs to say
that rather than "something went wrong" (`src/client/outcome.ts`).

**But the kit is pointed at the admin tier.** `GUARDED_PREFIXES`
(`OpenApiClientContractTest.kt:353`) is `/api/v1/admin/kg`,
`/api/v1/admin/handlers`, `/api/v1/hints`, `/api/v1/tours`. Meanwhile the surface
built for exactly the caller this note is about has no client at all:

| | |
| --- | --- |
| `POST /api/v1/views/{name}/invoke` | a saved query, called by name |
| `POST /api/v1/lenses/{lensId}/invoke` | plus `background` / `waitSeconds`, run polling |

`LensInvocationController` is the best-designed thing on the server for an
external consumer: identity from the authenticated principal only with no
`username` override, the runnable Cypher never exposed, and a deliberate
allow-list envelope (`PublicExecutionResult`) whose `outcome` vocabulary
distinguishes `EMPTY` from `SOURCE_UNAVAILABLE` — so a caller can tell "you have
none" from "a source is down" without seeing the internals. It is not guarded, not
in the snapshot, and not in the kit.

**Decided: guard it and generate it.** Add `/api/v1/views`, `/api/v1/lenses` and
`/api/v1/watches` to `GUARDED_PREFIXES`; add `client.views` / `client.lenses`.
Nothing is designed — the envelope, the pipeline and the skew model all exist.

## The calling-tier client

**Decided.** The calling tier gets its own client object, `embabel`, separate from
`ApplianceClient`. Not another namespace on the existing one: the two have
different audiences and different stability promises, and a third-party app should
never see `saveView`, `validate` or `generate`. `ApplianceClient` remains the
admin/studio client that me-app and the console are built on.

**One method, a serious name, typed by parameterizing the client with the generated
world.** No overloads, and no generated method-per-view file to keep in step:

```ts
export class Embabel<W extends WorldShape = UntypedWorld> {
  runView<K extends keyof W['views'] & string>(
    name: K,
    args: W['views'][K]['args'],
  ): Promise<Outcome<Result<W['views'][K]['returns']>>>
}

const embabel = Embabel.connect<MyWorld>({ baseUrl, credentials })
await embabel.runView('triage_dependencies', { policy: '…', minScorecard: 4 })
```

The generated `world.d.ts` is therefore a **type declaration only** — a map of view
name to `{args, rows}` or `{args, entities}`. Nothing generated is executable, which
removes the whole class of drift where a generated wrapper and the world disagree.
Each view's `returns` is written by the generator as either the shared entity type
or that view's own row shape — the `outputLabel` / `dataContract` exclusivity is
resolved at generation time, not by a conditional type. See "Language emitters"
below for why that choice is the portable one.

The default type parameter keeps the client usable before anything is generated
(`name: string`, loose args); adding `<MyWorld>` tightens it. One API, not two.

**Naming: `runView`, not `invoke`.** The endpoint is `/views/{name}/invoke` and the
admin sibling is `runView`; the client keeps `runView` for both because a method
should say what it does. Deferred lens execution takes an options object
(`background`, `waitSeconds`) rather than a second overload.

**No `query` and no `ask` on this tier, deliberately.** `LensInvocationController`
already refuses them — "Raw Virtual Cypher / NL-generation are deliberately absent
here; they remain a separate privileged surface." A caller that needs a query it
does not have saves a view. The surface enforces what the client skill could only
advise.

## Two contract layers, and one artefact cannot be both

This is the constraint that shapes everything else.

- **Envelope layer — world-independent.** OpenAPI, guarded snapshot, generated
  once into the kit. Invocation envelopes, error shapes, admin surfaces. Every
  appliance has the same one.
- **World layer — per-world.** View parameters and row types, entity types,
  method signatures. Generated from the *declared catalogue* into the consuming
  project as `world.d.ts`, fingerprinted. Valid only for that world.

The guarded-snapshot model only knows how to do the first. A per-world OpenAPI
document is the wrong instinct; `/apps-runtime/v1/contracts` is already the
per-world catalogue and already carries view contracts, so the world layer belongs
beside them. The generated file is checked into the consuming project the way a
Prisma client is — the published package can never carry it.

## Reads

**Decided: rows, not an object graph. No relationship navigation.**

A lazy `movie.director` that fires HTTP on property access is how an OO client over
a network API goes wrong, and traversal already has a correct home — a saved view,
server-side, where the join is validated, parameterised and cacheable. Client-side
navigation would reimplement precisely what `/views/{name}/invoke` exists to
provide.

### The two view shapes are mutually exclusive, by construction

`ViewSpec`'s `init` forbids `outputLabel != null && dataContract != null`. So a view
is one of two things and never both, and each takes its types from a different
place:

| Shape | Declares | Composes? | Types come from |
| --- | --- | --- | --- |
| **Node view** — `RETURN <singleVar>` | `outputLabel` | yes — inlines as `(v:name)` | the entity type catalogue |
| **Tabular view** — `RETURN a.x AS x, …` | `dataContract` | no — terminal | the view's ODCS contract |

This is cleaner than treating one as a special case of the other. Row types cannot
come from `/v3/api-docs` — `data` is a `JsonNode` because the spec cannot know a
view's columns — so a tabular view's columns come from its ODCS contract
(`POST /api/v1/admin/kg/views/{name}/contract`), versioned with the view. A node
view has no contract and needs none: its rows are entities of a declared type, and
that type is already in the catalogue.

Everything else in this section is about the tabular case; the node case is
"Obtaining a handle" below.

**When relationships arrive, they should probably not arrive as navigation** but as
typed traversal helpers that compile to a view invocation. Both that and typed
write-relations are additive to everything below.

**One rule to protect now:** when a `relationships` field lands on the type
catalogue, `[]` must mean "declares no outbound edges" and *absent* must mean "this
server does not declare them yet". That is the distinction the kit's `Outcome`
model draws with `unsupported`, and the same class of bug as a latch that cannot
tell "nothing found" from "never asked". So emit no `relationships` field at all
today — shipping `[]` now would burn the meaning.

## Parameters, and the AI ones

**Params reach everywhere, including into `{ai:{…}}`.** `InliningViewExpander:163`
substitutes textually before the parse —
`Regex("\\$name\\b").replace(acc, renderLiteral(v))`, strings rendered as
escaped single-quoted Cypher literals — so `$policy` resolves inside an edge
directive map exactly as it does in a `WHERE`. `ViewSpec.params` states the
guarantee explicitly.

That makes an intelligence view callable with caller-supplied judgement:

```yaml
params:
  policy: { type: string, description: The rule to judge each row against }
cypher: |
  MATCH (d:Dependency)-[:ASSESSED {ai: {hint: $policy, model: 'chat_cheap'}}]->(a)
  RETURN d.purl AS purl, a.verdict AS verdict, a.rationale AS rationale
```

A parameter with no `default` is required on invocation; one with a default is
optional. That is the whole rule generation needs, and it maps straight onto
optionality in the emitted args type.

Four constraints that generation and callers both have to respect:

- **A parameterized view cannot be materialized.** `ViewSpec.init` refuses it —
  "the cache is keyed per user, not per argument tuple". So every call to a
  parameterized AI view is a fresh model hop: `metrics.cacheHit` is always false and
  `durationMs` is model-bound. A cached AI view has to be unparameterized. Callers
  should be told this rather than discovering it from a latency graph.
- **`hint` is a reserved param name**, along with `ai`, `realm`, `userId`,
  `anchors`, `exclude`, `want` (`RESERVED_PARAM_NAMES`). The obvious name for an AI
  steering parameter is taken; it fails at declaration, not at run time.
- **Param types are `string` | `int` | `number` | `boolean`.** No lists, no objects.
  A policy is one string.
- **The `ai` namespace is closed** (`AI_NS_KEYS`: `hint`, `model`, `temperature`,
  `confidence`, `fresh`), and an unknown key inside it **logs a warning rather than
  failing**. A typo'd directive silently does nothing, which is the failure mode
  hardest to see from a client. `model` names a portable ROLE (`chat_cheap`,
  `code_best`), never a concrete model, and an unknown role falls back with a
  warning.

Generation should carry the first of those into the emitted docs: a view that
cannot cache is a different thing to call in a loop than one that can.

## Writes

**Decided: writes must be strongly typed.** Two candidate sources are wrong, and
the right one is already declared.

**Not the tool descriptor.** `create_entry`'s schema is `type: string`,
`data: OBJECT ("Fields to set")`, `relations: ARRAY of OBJECT`
(`RepositoryTool.kt:201-211`). The real shape lives in prose and in
`store.describe(type)`. Generating from it yields a type in name only.

**Not `/admin/kg/schema`.** `KgSchemaProperty` is "a property *observed* on nodes
carrying a label" with an "inferred type tag", and its optionality signal is
`sparse` — a sampling artefact. No identity key, no value domain, no validation.
Good enough to type reads; wrong for writes, because `sparse` says the sampler did
not see it, not that the server will accept its absence.

**Yes to `PropertySpec`** (`instance/types/PropertySpec.kt`), which declares per
property: `type`, `cardinality`, `required`, `identity`, `validation`, and `values`
(a fixed `list:`, or `source: distinct`). That maps to TypeScript almost
mechanically, and it is not aspirational: `RepositoryStore.writeOne` refuses a
missing required field atomically before writing anything, and an `identity`
property makes the write an idempotent MERGE.

```ts
export interface MovieProperties {
  imdbId: string               // identity → required, and the upsert key
  title: string                // required
  genres?: string[]            // cardinality: LIST
  status?: 'open' | 'closed'   // values.list → literal union
}
```

Four things that would otherwise bite:

- **`identity` belongs in the API shape, not just the type.** A keyed type's write
  is an upsert; calling it `create` misdescribes what re-running does.
- **`values: {source: distinct}` cannot become a union.** Only `values.list` is
  statically known. Emit `string` and leave the domain to runtime — the kit already
  has `kg.propertyValues(label, property)`. A union built from a sampled distinct
  set goes quietly wrong the first time the source grows a value.
- **Filter on `visibility`.** `internal` types are hidden from the repository tool
  surface, so generating write types for them offers writes the server refuses.
  `GET /api/v1/world/types` currently returns `dynamicTypes` unfiltered. Carry the
  flag rather than filtering, so an authoring UI can still see them.
- **Validation rules are JSDoc, not types.** `range` / `maxLength` do not survive
  into TypeScript. Emit them as documentation and let the server stay the enforcer;
  a client-side validator that can disagree with the server is worse than none.

**The blocker is a lossy projection, not a missing model.** `WorldController.kt:248`
maps each property to `{name, description}` — discarding type, cardinality,
required, identity, values and validation — and returns `List<Map<String, Any>>`,
so springdoc describes it as a bare object. A typed `WorldType` / `WorldTypeProperty`
DTO plus a `GUARDED_PREFIXES` entry is the whole fix. `DynamicType` lives in
embabel-agent, but nothing there needs to change: this is a projection the assistant
owns.

**Envelope the write body.** `{"data": {...}}`, not flat properties. A flat body
forces a reserved key (`_relations`) when relations arrive, which collides with any
property named that and is unfixable once worlds hold data. The envelope mirrors
the `{type, data, relations}` shape `RepositoryStore.create` already takes. One
nesting level now buys a purely additive future.

Scope note: typed creation is for the **import** case — bootstrapping entities that
methods can then act on. It is not the behaviour surface. That is below.

## What `runView` returns

**Decided: either recognized entity objects, or a shape generated for that one
view.** Never a bare row map, and never both for one view — `ViewSpec.init`
forbids `outputLabel` and `dataContract` together, so the case is always decided
by the declaration.

The two differ in more than shape. An entity type is **shared and named**: every
view returning `Dependency` returns the same interface, and it is the type bound
methods hang off. A view shape is **minted per view and named after it**, because a
projection belongs to the query that made it and to nothing else.

A node view is `RETURN <singleVar>` — whole nodes, not a projection. So an entity
handle is complete, and the earlier worry about half-populated entities does not
arise: a view that projects some columns of an entity is TABULAR, so it types as
that view's row shape rather than as a partial `Dependency`.

### Read and write types are not the same interface

`missingRequired` lives only in `RepositoryStore` (the `create` / `createAll`
path); `EntityProjection` has no `required` handling. So **`required` is enforced
on the repository write path only** — a producer-populated node can lack a property
its type declares required. `identity` is different, and its KDoc says so: the flag
"is already read by the population/projection path (`EntityProjection`), so one
declaration dedupes BOTH KG write paths".

| | `identity` | `required` | the rest |
| --- | --- | --- | --- |
| **Write type** | non-optional | non-optional | optional |
| **Read type** | non-optional | only when the type is repository-only | optional |

"Repository-only" is derivable: a `TypeEntry` declaring neither `population:` nor
`virtualJoins:` cannot arrive by a path that skips the guardrail, so `required` →
non-optional is sound for it. One that declares either can, so `required` → optional
on the read side.

The blanket alternative — marking every declared-required property non-optional on
reads — puts `undefined` behind a non-optional field for exactly the producer-backed
types realms are full of. That is the single failure a generated type exists to
prevent, so it is worth the extra rule.

## Methods — the heart of it

The object is not a DTO with setters. `Movie` is immutable; what you want on it is
`movie.rate("a masterpiece")` — behaviour that is natural on the graph.

Immutability falls out correctly: the object is a **frozen snapshot of properties
plus bound methods**. A method returns its declared output type, never a mutated
`self`, so you re-fetch to see new state. That is the right shape for an object
over a network and it is the same reasoning that rejected relationship navigation —
no lazy loading, no identity map, no hidden round-trips on property access. The
object is a handle with behaviour, not a live proxy.

### Obtaining a handle: two paths, both supported

**Decided: an app reaches an entity either by running a view that returns
entities, or by materializing one from an id.** Neither subsumes the other — a
view is how you find the ones you care about, an id is how you come back to one
you already know.

The declaration for the first mostly exists. A view declares `outputLabel`, and
`outputLabel == null` is precisely what makes a view TABULAR
(`GatewayViewTools.kt:20`); a materialized view with an `outputLabel` is already
usable as a query scope (`NamedViews.kt:65`). The envelope already has the
vocabulary too: `PublicResultProjector` emits `outputType = "entities"` for lens
results and carries them through `entitiesToJson`.

**The gap is on the view path only.** `LensInvocationController.invokeView` routes
through `fromAskResult`, which hardcodes `outputType = "rows"` regardless of the
view's declared `outputLabel`. So a view that declares it returns `Movie` still
arrives as a table. Making entity-returning views real means projecting entities
when `outputLabel != null` — small, but it changes `outputType` for existing
views, which is a wire change for anyone already parsing `rows`. Either the caller
opts in, or it rides a `contractVersion` bump. Not a silent flip.

**Identity is the price of a handle.** A method is bound to `(type, id)`, so an
entity you cannot identify is not an entity — it is a row. A view that projects
columns and drops the type's `identity` property yields rows no method can hang
off, and it should say so rather than returning something shaped like an entity
that cannot be acted on. **Rule: an entity handle requires its identity; a
projection that drops it yields rows.**

**A handle's properties are whatever arrived.** A view projecting three columns
gives a `Movie` handle carrying three properties, not a full snapshot. The methods
are complete either way — they only need the id — but the property surface is not.
Generation should reflect that honestly: the full `MovieProperties` only where the
contract declares every property, otherwise a partial snapshot plus the identity.
An entity materialized by id is the one path that can promise the full set. Typing
a partial projection as complete would put `undefined` behind a non-optional field,
which is the one failure a generated type exists to prevent.

### Two method models exist, and neither alone is enough

| | Realm-authorable | Typed | Bound invocation |
| --- | --- | --- | --- |
| JVM `@LlmTool` methods | no — Kotlin, host code | yes | **yes, today** |
| Realm specs (`actions/`) | yes | yes | no |

`POST /api/v1/program/invoke-method` (`ProgramMethodController`) already does bound
invocation — its own comment says it is what the sandbox's `state.js` proxy POSTs
"when the LLM calls `bill.isOverdue({ asOf })` on an in-scope binding". It is even
reachable with ordinary credentials, since `SandboxApiKeyFilter` falls through when
no key header is present, leaving Basic Auth to authenticate normally.

Three reasons it is not the answer:

1. The methods are JVM `@LlmTool` methods on Kotlin classes. Realms are authored in
   YAML and TypeScript, so realm behaviour would mean host code changes — again per
   realm. Wrong place.
2. **The caller supplies the object's state.** `invoker.invoke(req.type, dataJson, …)`
   reconstructs the instance from posted JSON. Fine for a sandbox holding an object
   from a trusted read; wrong for an external client, where it means the client
   asserts what the Movie *is* rather than naming which node to act on.
3. It is `@Hidden` — absent from OpenAPI, so no generated types and no contract
   guard.

**Priority: TypeScript realm methods.** JVM methods are the built-in special case,
and the same endpoint can dispatch to them.

### What a realm TypeScript body sees today

The complete ambient contract (`src/main/resources/typescript/validate-globals.d.ts`):

```ts
const gateway: GatewayContext
const signal: SignalEnvelope | null
const trigger: "signal" | "cron"
const now: string
const dryRun: boolean
const console: Console
```

**No subject, no args, no return.** `trigger` is a two-value union — the type itself
says a realm action is *triggered*, never *called*. `review_brief.yml` binds
`signalType: GitHubReviewRequested`; `stale_reviews.yml` binds a `schedule`. Those
are the only two ways in. A body reads `signal`, calls `gateway.*`, and logs what it
did.

The vocabulary for binding a subject does exist elsewhere in the codebase: the
`GatewayActionSpec` sibling declares `inputTypeNames` / `outputTypeName` /
`outputCardinality` (`realm-github/actions/list_commits_for_person.yml` is literally
`person.listCommits(): CommitActivity`). It is the *TypeScript* variant that lacks it.

### The delta

- **On `TypeScriptActionSpec`:** a declared subject type, declared typed parameters,
  a declared return type.
- **In the ambient contract:** `subject` (bound entity, typed), `args` (declared
  parameters, typed), a return channel, and `trigger: "signal" | "cron" | "call"`.
- **One endpoint:** `POST /api/v1/types/{type}/{id}/methods/{name}` — the server
  loads the subject by id, so identity and authority stay server-side — answering
  `PublicExecutionResult`, the same envelope and redaction seam as view invocation.

That is the whole feature. No new subsystem.

### Decisions this forces

**`dryRun` inverts.** The realm-action convention is that every external effect sits
behind `if (!dryRun)` — `review_brief.ts` says so in its header, "observe-only until
adopted AND promoted". Right for something a scheduler runs unattended; exactly
wrong for a called method, where `movie.rate(...)` silently doing nothing is a trap
the caller cannot see. For a call, the call **is** the intent: `dryRun` becomes an
explicit caller choice, not an authoring-lifecycle default.

**`autonomous` loses its meaning.** It governs unattended execution. When a caller
invokes a method the caller is the authority, so either the flag does not apply to
methods or it means something new. It must not quietly carry over.

**A top-level script has nothing to return from.** The body is a script, not a
function. Either the runtime wraps it implicitly or the contract gains an ambient
`result` the body assigns. Wrap it: an assigned-global convention works until
someone writes an early exit and silently gets `undefined`.

**Multi-input actions have no natural receiver.** `inputTypeNames` is a list. An
action over `[Person, Repo]` is a method on neither. Rule: single input → a method
on that type; multiple → a free function (`world.actions.x(person, repo)`). Guessing
a receiver from position produces an API that reads wrong half the time.

**Bound invocation is a second execution mode, not a shortcut into the first.** The
planner can chain actions to reach a goal and fans out over collections
(`CardinalityInserter`). A bound call deliberately does none of that: one action,
once, on one node. Say so rather than letting callers assume planning.

### Why this is cheaper than it sounds

The realm-author side is already built.

- `TypeScriptValidator` typechecks each body against the per-user generated
  `gateway.d.ts` plus those ambient globals, so a wrong `subject` field or mistyped
  arg becomes a compiler error the moment they are declared. No new validation.
- `TypeScriptActionTypeProvisioner` already generates `handler-context.d.ts` per
  action. Generating `subject: Movie` into it from the declared type is that same
  mechanism.
- Authoring over REST is already typed and guarded: `/api/v1/admin/handlers` is in
  `GUARDED_PREFIXES` and ships in the kit as `HandlersClient`.

So the realm author gets typed `subject` / `args` in their editor and the TypeScript
client gets the mirror image, both generated from one declaration. That single
source is the property that makes this worth doing at all — it is the same argument
that put the kit between the two front ends.

It also lands symmetrically with what exists: `/views/{name}/invoke` is a saved
*query* called by name; this is saved *behaviour* called by name with a subject.
Same envelope, same redaction seam, same rule that a consumer never submits
executable code.

## Language emitters

**The architecture already exists and is proven.** `GatewayCodeSurfaceBuilder` is
an interface with four implementations — `JavaScriptCodeSurfaceBuilder`,
`PythonCodeSurfaceBuilder`, `WasmJsCodeSurfaceBuilder` and an Html no-op — turning
one set of tool descriptors into per-language typed surfaces. Python's already
emits keyword-argument stubs with docstrings
(`prompts/codemode/python/interfaces.jinja`) over a `requests`-based gateway
module. The world-layer generator should copy that shape: **one catalogue, N
emitters.**

Nothing decided in this note is TypeScript-specific. `ViewParamSpec`,
`PropertySpec`, the `outputLabel`/`dataContract` exclusivity and the read/write
optionality rule are language-neutral facts about the world. Only the rendering
differs. **The risk to guard is the intermediate model absorbing TypeScript
assumptions** — structural typing, `undefined`-as-absent — which would make every
later emitter fight it. The model should be the declared world, not a TS shadow of
it.

### Do not transliterate

The TS shape (`runView(name, args)` typed through `keyof` over a mapped type) is
right for TypeScript *because* TypeScript has no named parameters. Python has
keyword arguments, defaults and docstrings, so the view name belongs in the
function name — which is already what `PythonCodeSurfaceBuilder` does for tools:

```python
embabel.views.triage_dependencies(policy='…', min_scorecard=4)
```

Declaration-only generation survives: a generated `.pyi` over a generic
`__getattr__` runtime, exactly as `world.d.ts` sits over a generic client.

### The entities/rows choice belongs to the EMITTER, not the type system

Earlier drafts expressed it as a TypeScript conditional type (`Yield<…>`). Drop
that. Which case a view is, is settled at GENERATION time by its declaration —
`outputLabel` or `dataContract`, never both — so the emitter simply writes the
right return type. TypeScript can do it either way; no other language can do it
with a conditional type at all. Choosing the emitter form keeps one rule across
every language and makes the TS output simpler too.

### `Outcome` in TypeScript, exceptions in Python

`Outcome<T>` exists because two FRONT ENDS must render "your appliance predates
this" without a stack trace. A script wants to fail loudly instead. So the failure
model is idiomatic per language — a small exception hierarchy in Python
(`ApplianceUnsupported`, `ApplianceUnauthorized`, `ApplianceUnreachable`), the
union in TypeScript — while the EXECUTION envelope (`outcome`, `warnings`,
`metrics`) is returned identically in both. Same information; the transport-level
failure is what changes shape.

This also dissolves the two-level check that reads badly in TypeScript
(`isOk(r)` then `r.value.outcome`): Python has one level naturally, and TS should
get a narrowing helper rather than a flattened model.

### Which languages, and when

**Decided now:** TypeScript and Python.

**Next, on merit:** **Java/Kotlin.** The whole ecosystem is JVM — `embabel-agent`,
`java-agent-template`, `kotlin-agent-template` — so an Embabel AGENT calling an
appliance is the most likely third consumer, and it is the one audience whose
toolchain the team already knows. One hazard to design for up front: a `values.list`
domain rendered as a Java/Kotlin `enum` becomes a breaking change the moment the
realm adds a value. Render it as constants plus validation, or accept unknown
values, but do not let a growing domain break recompilation.

**Cheaper than any third language, and probably first:** the **CLI**. `embabel`
already has `contract generate --view`; an `embabel run-view <name> --arg …`
emitting JSON serves shell, CI and cron consumers with no emitter, no package and
no release train. Worth doing before a third language is considered.

**Demand-gated, not architecture-gated:** C#/.NET (matters enormously to a .NET
shop and not at all otherwise) and Go (infra consumers — an exporter, an operator,
a sidecar). Both are real, neither is evidenced yet.

**Probably never:** Rust, Ruby, PHP — no consumer in sight, and each is a permanent
maintenance obligation.

**The governing rule**, borrowed from the kit's own guardrail in
`SHARED_CLIENT_DESIGN.md`: nothing enters until a real consumer needs it. An
emitter with no consumer is a second surface to keep in step with every change to
the world model, paid for indefinitely by the people who do have consumers.

## Order of work

1. Guard and generate `/views`, `/lenses`, `/watches`; add `client.views` /
   `client.lenses` to the kit. Small, independent, unlocks the caller tier today.
2. Typed `WorldType` DTO and a non-lossy `/api/v1/world/types`, guarded. Prerequisite
   for any generation, and useful alone.
3. Subject / args / return on `TypeScriptActionSpec` and the ambient contract.
4. `POST /api/v1/types/{type}/{id}/methods/{name}`, plus entity projection for
   views declaring an `outputLabel` — the two ways to get a handle.
5. Codegen: catalogue → `world.d.ts`. Types become interfaces, methods hang off their
   subject type.

Steps 1 and 2 commit to nothing in 3–5.

## Open questions

- `dryRun` as an explicit caller choice: does a realm get to refuse it — declare
  "this method has no meaningful dry run" — or is it always honoured?
- Where does the generated `world.d.ts` come from at build time: a live appliance
  (needs credentials in CI) or a committed catalogue snapshot regenerated by a job,
  the way the client-surface snapshot already works? The snapshot precedent argues
  for itself.
- `POST /api/v1/program/invoke-method` stays `@Hidden` and sandbox-shaped, or does
  the new endpoint absorb it? Absorbing means one dispatcher and one envelope;
  leaving it means two ways to call a method, which is how drift starts.
- Contract version: methods are additive to `/apps-runtime/v1/contracts`'s
  `contractVersion: "1"`, so no bump. Confirm nobody bumps it reflexively.
